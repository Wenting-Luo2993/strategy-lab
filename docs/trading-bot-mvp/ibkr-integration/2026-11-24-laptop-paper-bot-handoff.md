## Phase A: prepare the laptop without broker login

### 1. Establish hardware and supported platform

Record the actual CPU architecture, RAM, free physical disk and OS support.
Use a supported, updated Windows/Docker/WSL combination; an old Windows version
being able to install WSL is not sufficient Docker Desktop support.
Consult [Docker's Windows requirements](https://docs.docker.com/desktop/setup/install/windows-install/)
and [Microsoft's WSL setup](https://learn.microsoft.com/en-us/windows/wsl/install).
Verify the pinned Gateway image supports the device architecture rather than
silently adding emulation.

The starting compute recommendation is about **2 CPUs and 8 GB available to
the Linux runtime**, subject to hardware and measured pressure, not a proven
minimum. Windows needs headroom too; do not allocate all of an 8 GB laptop to
WSL or declare success by adding swap. Review inadequate hardware with the user
before migration. Docker's own platform requirements still apply.

These are read-only Windows PowerShell checks:

```powershell
Get-CimInstance Win32_ComputerSystem | Select-Object NumberOfLogicalProcessors,TotalPhysicalMemory
Get-CimInstance Win32_OperatingSystem | Select-Object Caption,OSArchitecture,Version
Get-PSDrive C | Select-Object Name,Free
wsl --version
wsl --list --verbose
docker version
```

Install missing prerequisites only with operator approval. For a fresh approved
WSL installation, use `wsl --install -d Ubuntu` in an elevated PowerShell, reboot
if requested, and let the operator complete Ubuntu's user/password prompts.
Do not overwrite an existing distro. Install Docker Desktop from the official
source, select Linux containers/WSL2, and enable Ubuntu under Settings ->
Resources -> WSL Integration. Do not install a competing Docker daemon in
Ubuntu. Review saved containers before starting Docker Desktop: restart policies
may revive a previous deployment.

### 2. Use a non-root Linux deploy user and isolated main clone

Enter Ubuntu interactively with `wsl -d Ubuntu`. All subsequent Bash commands
run **inside Ubuntu**, not Windows PowerShell or Git Bash. Explicitly `cd` to
the runtime checkout; do not rely on inherited Windows working directories or
inline `$HOME` interpolation across the two shells.

Use an existing suitable non-root user where possible. Both images use UID
1000; check `id` and `getent passwd 1000`. If a new deploy user is needed, follow
the canonical WSL procedure only after confirming no UID/name conflict.
The operator enters passwords privately. Docker access is effectively
privileged: grant it only to the intended deploy user. Do not run the harness
as root or use `sudo` to bypass missing Docker access.

For a new, unused destination directory:

```bash
git clone --branch main --single-branch https://github.com/Wenting-Luo2993/strategy-lab.git "$HOME/strategy-lab"
cd "$HOME/strategy-lab"
git fetch origin main
git pull --ff-only origin main
git branch --show-current
git status --short --untracked-files=no
git merge-base --is-ancestor 45fb3f0 HEAD
git rev-parse HEAD
docker info --format 'CPUs={{.NCPU}} MemoryBytes={{.MemTotal}} OSType={{.OSType}}'
docker compose version
docker ps -a --format '{{.Names}} {{.State}}'
command -v git curl python3 flock
free -h
df -h /
```

Every command must succeed where applicable; confirm `main`, a clean tracked
tree and the intended image architecture. If a checkout already exists, inspect
it rather than re-cloning over it or resetting files. Keep runtime data on
Linux storage, not `/mnt/c`. Use `~/strategy-lab` only as the dedicated runtime
clone, not an app-managed coding worktree.

Refresh [Deploy Guardrails](https://github.com/Wenting-Luo2993/strategy-lab/actions/workflows/deploy-guardrails.yml)
for the actual deployment revision if main has advanced. The old green run
does not certify a new release. Preserve fixes for durable order identity and
publisher recovery; do not roll back to the pre-portfolio bot.

### 3. Build images without starting containers

From the clean main runtime root:

```bash

docker pull ghcr.io/gnzsnz/ib-gateway:10.50.1f@sha256:1e2236804ac949b789197c225a048c0c891c9958f948c87166226e5b647ff581
docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}} {{.Created}}' strategy-lab-trading-bot:local
```

The Gateway reference above matches main `45fb3f0`. If it has changed, review
and use the tag **and digest** in the current production Compose file.
Capture build exit codes and image IDs. Image download/build is preparation,
not a successful deployment. No raw `docker run`, `docker compose up`, restart,
login probe or manual warm-up is allowed here. The root `.dockerignore`
excludes deployment secrets/data and local temporary artifacts.

Create the canonical `data/trading-bot`, `logs/trading-bot` and
`state/tws_settings` directories with UID 1000 ownership. Operator-approved
credential preparation can use the hidden helpers in the runbook; never read
real secret files or render `docker compose config` with resolved values.
`config --quiet` is the supported validation form. Do not overwrite migrated
configuration with the example env file.

Before private files exist, `deploy.sh check` will correctly fail the missing
secrets check. Record that exact pending prerequisite; do not create fake
production credentials or call a partial preflight a pass. Resolve it before
starting the stack.

### 4. Agree and verify continuous-operation settings

Use a reliable AC adapter, stable network and adequate ventilation; an old
battery is not a substitute for reviewing device condition. Get operator
approval before changing AC sleep, hibernation, lid-close behavior, scheduled
updates or startup settings. Keep screen locking and security protections;
do not disable Windows updates or configure insecure automatic login.

Configure Docker Desktop startup and prove the required Windows sign-in and
WSL availability after reboot. `restart: unless-stopped` does not start Windows
or Docker Desktop by itself. If restart needs manual sign-in, report that
operational limitation rather than claiming unattended recovery. Test laptop
lid/network/power behavior before cutover, while no trading service is active.
Retain bounded logs, monitor disk/pressure and agree alert/review ownership.

**Report "prepared, not started"** with laptop hardware, Linux memory budget,
clean main SHA, green guardrails, image IDs/build results, Docker/WSL access,
power/reboot limitations and pending private-state/credentials requirements.
Stop here for the user/coordinator's cutover decision. Laptop startup must wait
until the source is confirmed stopped; broker login cannot be part of this
readiness gate.

## Phase B: later approved cutover

This is the supported future procedure, **not an instruction to execute now**.
The user/coordinator handles Oracle's stop after accepting Phase A evidence.
Operate outside weekday 09:25-16:05 America/New_York and refresh time, code,
source status and exposure immediately before the change. Obtain separate
approval for any incident market-hours override.

1. Review fresh broker positions and working orders through the existing
   authorized view; do not start a competing Gateway to check them. A restart
   does not flatten positions. If exposure is unknown or no longer flat,
   pause for an explicit management/migration decision.
2. In the operator's SSH terminal as `ubuntu` in `/opt/strategy-lab`, run
   `deploy.sh status` and `check`. If needed, update the clean source only with
   `git pull --ff-only origin main`, then recheck. After specific stop approval,
   run `bash deploy/ibkr-docker/deploy.sh stop`. Require exit 0 and
   `Stack stopped`; confirm both source containers are not running and legacy
   services/timer remain inactive/disabled. This stops bot before Gateway and
   preserves the Oracle instance and persistent files.
3. Only with writers stopped, arrange a separately approved, direct encrypted
   private transfer from Oracle to the **laptop**, not via this research PC
   or a public/cloud upload. The previous transfer question was not answered:
   no copy method or credentials transfer is pre-authorized. The operator
   copies/enters secrets; agents never open them. Preserve originals.
4. Restore the full durable directories listed below; verify private file
   inventory/hashes and SQLite integrity through an approved check before
   opening destination writers. Copy all database files and companions while
   stopped or use a consistent SQLite backup; a live `.db`-only copy can omit
   WAL transactions. If destination has prior bot data, stop for review instead
   of overwriting or merging journals.
5. Confirm source still stopped, correct ownership, matching paper/account and
   publisher configuration, then run destination `deploy.sh check`. It must
   actually pass. Ask separately for laptop `gateway` approval, then run
   `bash deploy/ibkr-docker/deploy.sh gateway` from the non-root main checkout.
   Require exit 0 and `Gateway + bot OK`; retain sanitized evidence.

## Runtime verification and collection gate

Record actual code SHA, image ID, version and UTC/ET start time, then run the
canonical status procedure. Never dump container environments, raw secret-bearing
logs or account balances into chat/Git. Verify these layers separately:

| Layer | Required evidence |
| --- | --- |
| Exclusive ownership | Oracle stopped; one laptop bot/Gateway; no old PC trading stack or external competing login |
| Process liveness | Both containers healthy; `/api/health` 200; startup markers from this start |
| Broker reconciliation | Correct paper account, successful execution-client recovery and broker/journal agreement; no stale phantom exposure or duplicated protective exits |
| Scheduled readiness | Real warm-up and session equity state; per-symbol fresh/completed data. Off-hours `/health/ready` 503 and absent live ticks are not deployment failures |
| Durable collection | New traceable orders/fills, benchmarks, commissions, local persistence and publisher progress; dashboard bars alone are insufficient |
| Full-session behavior | End-of-day broker positions/orders reconciled, final bars retained, parity/cooldown and alerts delivered; failures and exclusions disclosed |

Keep `orb_resting_stop_paper_5sym` unchanged: **QQQ, AMZN, GOOGL, MSFT, TSLA**,
5-minute opening range, symmetric resting stops with broker-side protection,
no profit target, entry cutoff 15:00 and EOD exit 15:55 ET. This is not the
15-minute entry-confirmation research experiment. Preserve 1% per-trade risk,
20% per-symbol exposure cap, 1x gross leverage, five positions and 3% daily
loss limit. No higher-risk settings are implied by moving hosts.

Observe **three consecutive complete, reconciled sessions** before reviewing
ten-symbol expansion. This is an operational shakedown, not statistical proof.
Review additional symbols/entitlements and version the new configuration
separately; the existing five-position/headroom caps can prevent more symbols
producing more fills. Do not silently increase leverage, risk or concurrency.
Separate added-symbol observations and disrupted sessions; retain valid adverse
fills and assess entry versus protective-exit slippage separately. Paper fills
and correlated same-day samples cannot establish real-money queue position,
slippage or profitability.

More headroom may alleviate Oracle resource pressure, but does not fix the
unresolved upstream/session-conflict, reconciliation, timing and data-quality
problems by itself. Keep those incident follow-ups open until observed evidence
supports closure.

## Failed start or return to Oracle

If the laptop start fails, do not launch Oracle concurrently or repeatedly
recreate journals. Preserve evidence, follow the incident guide and obtain
approval for the recovery action. For a failback, stop the laptop through its
harness first, reconcile/transfer its newer durable state privately, then get
approval for Oracle `gateway`. Oracle's retained but outdated journal is not
safe failback state. Never delete the Oracle instance as cleanup.
